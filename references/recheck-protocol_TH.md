# Re-check Protocol (สรุปภาษาไทย)

งานที่ออกมาไม่ดีส่วนใหญ่ ไม่ได้เกิดจากโมเดลทำไม่เป็น แต่เกิดจาก **หยุดก่อนหนึ่งก้าว** — ทำงานเสร็จ เกิดความรู้สึกว่า “น่าจะโอเค” แล้วรายงานความรู้สึกนั้นออกไป

Re-check คือการเอาความรู้สึกนั้นออก แล้วแทนด้วยการตรวจงานตัวเองแบบไม่เข้าข้าง

```bash
npm run recheck -- plan --mode design-ui      # ขอรายการตรวจ
# ทำตามรายการ แล้วเขียนบันทึก
npm run recheck -- audit --record .fx/recheck.json
```

คำสั่ง audit จะ exit ไม่เป็นศูนย์ตราบใดที่ re-check ยังไม่พอ งานที่ตรวจตัวเองไม่ครบจึงเสนอเป็นงานเสร็จไม่ได้

## สี่คำถามหลัก (ต้องเขียน ไม่ใช่คิดในหัว)

1. **ฉันกำลังเคลมอะไรบ้าง** — เขียนทุกประโยคที่จะบอกผู้ใช้ออกมาทีละข้อ ข้อที่เขียนไม่ออก คือข้อที่ยืนยันไม่ได้
2. **อะไรพิสูจน์แต่ละข้อ** — ผูกทุกประโยคกับผลคำสั่ง ไฟล์ หรือภาพ ข้อที่ไม่มีหลักฐานให้ลบ หรือลดเป็น “ยังไม่ได้ตรวจ”
3. **ถ้าฉันผิด ฉันจะรู้ได้ยังไง** — เอาข้อที่มั่นใจที่สุดสองข้อ ระบุว่าเห็นอะไรแล้วจะแปลว่าผิด แล้ว **ไปหาสิ่งนั้นจริง ๆ**
4. **มีอะไรที่ไม่ได้ดูเลย** — ระบุ state, path, seed, breakpoint, มุมภาพ ที่ไม่ได้ตรวจ การเงียบเรื่องพื้นที่หนึ่งไม่ใช่หลักฐานว่าพื้นที่นั้นดี

## ทำไมต้องพยายามหักล้างตัวเอง

“ไม่เจอปัญหา” กับ “หาแล้วไม่เจอ” ไม่เหมือนกัน verdict ว่า clean โดยไม่มีร่องรอยการหา คือความรู้สึกที่ใส่เสื้อคลุมว่าเป็นข้อสรุป — ตัว audit จะปฏิเสธ

ถ้า **ตรวจงานตัวเอง** เกณฑ์สูงขึ้น: ต้องพยายามหักล้าง 3 ครั้ง (แทน 2) และต้องเขียน “อะไรจะทำให้ฉันเปลี่ยนใจ” ด้วย

## สิ่งที่ audit บล็อก

| Code | เหตุผล |
|---|---|
| `RECHECK_CLAIM_UNBOUND` | มีประโยคในรายงานที่ไม่มีอะไรรองรับ |
| `RECHECK_CLAIM_OVERSTATED` | ใช้คำเด็ดขาด เช่น pixel-perfect, production-ready บนหลักฐานบาง ๆ |
| `RECHECK_CLAIM_IMPRESSION` | “น่าจะได้” “ดูโอเคแล้ว” — ความรู้สึกที่รายงานเป็นข้อค้นพบ |
| `RECHECK_CHECK_WITHOUT_OBSERVATION` | ติ๊กว่าตรวจแล้วแต่ไม่มีสิ่งที่เห็น |
| `RECHECK_TOO_SHALLOW` | ตรวจจริงน้อยกว่า 4 ข้อ |
| `RECHECK_NO_ADVERSARIAL_PASS` | ไม่มีความพยายามพิสูจน์ว่าตัวเองผิด |
| `RECHECK_CLEAN_WITH_OPEN_ISSUES` | verdict ขัดกับสิ่งที่เจอเอง |
| `RECHECK_BLIND_SPOTS_MISSING` | ทุกงานมีมุมที่ไม่ได้ดู ต้องบอกออกมา |
| `RECHECK_ARTIFACT_IDENTITY_MISSING` | ตัดสินจากไฟล์ที่พิสูจน์ไม่ได้ว่าเป็นเวอร์ชันปัจจุบัน |

## กฎการหยุด

เจอปัญหาตอน re-check → **แก้ก่อนเสนอ** ห้ามเสนองานแล้วใส่ปัญหาไว้ท้ายเป็นเชิงอรรถ เพราะนั่นคือการโยนงานที่ยังไม่เสร็จให้ผู้อ่าน

ข้อยกเว้นคือปัญหาที่แก้ในขอบเขตนี้ไม่ได้จริง ๆ → ระบุเป็น open issue พร้อมความรุนแรง ตั้ง verdict เป็น `issues-found` และบอกตรง ๆ ว่าอะไรยังไม่ได้พิสูจน์

## ระดับความลึก

| Depth | ใช้เมื่อ |
|---|---|
| `quick` | งานเล็ก ความเสี่ยงต่ำ ย้อนกลับได้ |
| `standard` | ค่าเริ่มต้น: ครบทั้ง 8 ข้อ + ข้อเฉพาะโหมด + รันเกตซ้ำบนไฟล์ปัจจุบัน |
| `deep` | งานที่ย้อนไม่ได้ เกี่ยวกับความปลอดภัย หรือผู้ใช้เห็นชัด |

ลดความลึกได้ แต่ลดความซื่อสัตย์ไม่ได้ — ข้อผูกหลักฐานกับข้อตรวจภาษาอยู่ในทุกระดับ

## จุดเชื่อม

- ไม่มีโหมดไหนปิดได้ถ้าไม่ทำ (`references/operating-modes_TH.md`)
- ป้อนเข้ารายงานปิดงานโดยตรง: residual risk และช่องที่ยังไม่ได้ตรวจ มาจาก blind spots และ open issues
- **ไม่ได้แทนการรีวิวอิสระ** — re-check คือผู้เขียนซื่อสัตย์กับตัวเอง ส่วนรีวิวคือคนอื่นที่เป็นอิสระ
