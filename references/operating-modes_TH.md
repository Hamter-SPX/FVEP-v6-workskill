# โหมดการทำงาน (สรุปภาษาไทย)

โหมดไม่ใช่ “บุคลิก” แต่คือ **สัญญาของงานช่วงนั้น**: ทำอะไรได้, ยังห้ามทำอะไร, ต้องรันเกตอะไรถึงจะมีหลักฐาน, และต้องจริงข้อไหนบ้างถึงจะปิดโหมดได้

มีโหมดเพราะความผิดพลาดที่พบบ่อยที่สุดคือ **ไถลออกนอกงาน** — ถามเฉย ๆ กลายเป็นรื้อโค้ด, หาแนวทางดีไซน์กลายเป็นเขียนโค้ดจริง, แจ้งบั๊กกลายเป็นรีดีไซน์ ทุกการข้ามเส้นแบบนี้ต้อง “เห็นได้”

```bash
npm run mode -- list
npm run mode -- show design-ui
npm run mode -- resolve "ช่วยรีดีไซน์หน้านี้ให้หน่อย"
npm run mode -- check --mode match-ref --state .fx/mode-state.json
```

## สิบโหมด

| โหมด | ไว้ทำอะไร | ปิดได้เมื่อ |
|---|---|---|
| `analyze` | เข้าใจก่อนแตะอะไร | เล่าโจทย์ใหม่ได้ตรง + ระบุความเสี่ยงและสิ่งที่ยังไม่รู้ |
| `design-ui` | เลือกทิศทางภาพที่ตรวจสอบได้ | ผู้ใช้เลือกตัวเลือกเป็นตัวเลข และยืนยัน **เริ่มเขียน** |
| `match-ref` | ทำให้ตรงกับต้นฉบับ | `vision:triage` คืน `verdict=match` หรือผู้ใช้ยอมรับส่วนต่างที่เหลือ |
| `design-game` | ฉาก เลเวล แมพ asset | เกตฉากและ asset ผ่าน พร้อมภาพจากในเกมจริง |
| `implement` | ลงมือสร้างตามที่อนุมัติ | ทุก task มีหลักฐาน RED/GREEN |
| `debug` | หาขอบเขตที่พัง | ระบุ root cause + เทสต์ regression ที่แดงก่อนแล้วเขียว |
| `review` | ตรวจงานคนอื่น | มีทั้ง spec verdict และ quality verdict |
| `ship` | เปลี่ยนงานเป็นการตัดสินใจปล่อย | เสนอทางเลือก โดยไม่เลือกแทนผู้ใช้ |
| `author-skill` | แก้ตัวสกิลเอง | ของใหม่มีเทสต์ที่ “ตกถ้าไม่มีมัน” |
| `recover` | ต่องานที่ context หาย | ระบุ phase ปัจจุบันจาก artifact ไม่ใช่จากความจำ |

## เข้าโหมด

`npm run mode -- resolve "<ข้อความ>"` ให้คะแนนจากคำ trigger ทั้งไทยและอังกฤษ แล้วบอกโหมด ระดับความมั่นใจ และต้องถามยืนยันไหม

ถ้าไม่เจอสัญญาณ หรือสองโหมดคะแนนใกล้กัน จะ exit ไม่เป็นศูนย์ เพราะการเข้าโหมดผิดคือต้นเหตุที่ Agent ไปแก้โค้ดทั้งที่ผู้ใช้แค่ถาม

โหมดปลอดภัยที่สุดคือ `analyze` — เป็นโหมดเดียวที่เข้าได้เลยโดยไม่ต้องถาม

## ออกจากโหมด

`npm run mode -- check` จะไม่ยอมให้ปิดโหมดเมื่อ:

- ยังไม่ได้รันเกตที่บังคับ
- ทำสิ่งที่โหมดนั้นห้าม
- ขาดคำยืนยันจากผู้ใช้ (เช่น **เริ่มเขียน** ก่อนลงมือ)
- ยังไม่ได้ทำ re-check

## การข้ามโหมด

```text
analyze  → design-ui | design-game | implement | debug
design-ui → implement          (หลัง 「เริ่มเขียน」 เท่านั้น)
design-game → implement | match-ref
implement → debug | review
debug → implement
review → implement | ship
ship → recover
recover → โหมดใดก็ได้ หลังระบุ phase ได้แล้ว
```

**ประกาศทุกครั้งที่ข้าม** เช่น “กำลังย้ายจาก analyze ไป implement” — ประโยคนี้ผู้ใช้เบรกได้ทัน และนั่นคือจุดประสงค์

## โหมดไม่ได้แทน router

`npm run process:route` ยังเป็นตัวเลือกวินัยและ blocker ของงานข้างล่างเหมือนเดิม โหมดอยู่ชั้นบนในฐานะสัญญาที่คุยกับคน: โหมดบอกว่า “ช่วงนี้ทำเพื่ออะไร” ส่วน router บอกว่า “ช่วงนี้ข้ามหลักฐานอะไรไม่ได้”

## ทุกโหมดต้องผ่าน re-check

ไม่มีโหมดไหนปิดได้โดยไม่ทำ re-check (ดู `references/recheck-protocol.md`) แต่ละโหมดมีข้อตรวจของตัวเองเพิ่ม เช่น `design-game` ต้องดู asset เป็นเงาดำที่ 64px, `match-ref` ต้องยืนยันว่าไม่ได้ไปลด tolerance เพื่อให้ผ่าน
